# MOD-02 Identity — sign-in, session lifecycle, permission and scope assignment, and staff
# deactivation are enforced (BR-IAM-001/002/003/004/005/006/007/008/009/011/012). What remains
# is one behaviour with no single enforcement point:
#   010  a person may hold both guardian and staff roles, with independent rights. The data model
#        allows it (one users row, several user_roles; guardian rights from guardian_student_links,
#        staff scope from user_scopes) but nothing asserts the two resolve independently — that
#        needs a test exercising both role paths for one user, and under the current no-test policy
#        it stays listed until one lands.
#
# BR-IAM-001 came off with CurrentActorArgumentResolver (@BusinessRule): a controller's
# CurrentActor is the authenticated session's, and a client-supplied actor id is not consulted.
#
# BR-IAM-003/006 came off with role assignment (V3 user_roles, V15 user_scopes):
# ChangeAdministrativeUserRoleUseCase and CreateAdministrativeUserUseCase hold an administrator to
# one role within one organization and pair it with the scope that role permits. Enforcing the
# read-time scope predicate across every consuming module (BR-IAM-006's other half) is per-module
# work carried in each module's own rows, not here.
#
# BR-IAM-008 came off with SetAdministrativeUserStatusUseCase and DeactivateStaffUseCase:
# deactivation revokes every session in the same transaction, and staff deactivation also clears
# standing duty assignments.
#
# BR-IAM-004 came off this list with permission enforcement (V14): PermissionEnforcementInterceptor
# resolves permissions from current role assignments on every request rather than from the token.
#
# BR-IAM-012 came off this list with MOD-03: GetStudentUseCase writes a data-access record
# for every non-guardian read, in the reader's own transaction.
#
# BR-IAM-005 came off this list with MOD-18: the parent dashboard scopes every read through
# guardian_student_links, and ParentDashboardScopeIT holds it to that.
